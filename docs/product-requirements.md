# プロダクト要求定義書 (Product Requirements Document)

## プロダクト概要

### 名称
**Horecast** - AI競馬予想Webアプリケーション

### プロダクトコンセプト
- **マルチLLM予想表示**: OpenAI・Claudeなど複数のLLMが生成した予想結果をSupabaseから取得して表示する
- **拡張可能なテーブル設計**: 将来的に新しいLLMプロバイダーを追加してもスキーマ変更なく対応できる設計
- **統合された予想UI**: 既存のレース詳細画面にLLM予想コンポーネントをシームレスに組み込み、一覧性の高い比較表示を実現

### プロダクトビジョン
Horecastは、複数のLLMが生成した競馬レース予想をユーザーが一画面で比較できる競馬予想プラットフォームを目指す。
LLMによる予想結果はユーザー（オーナー）がSupabaseに格納し、HorecastはそのデータをAPIで取得してUIに表示する責務を担う。
現在の出馬表・AI予想スコア表示に加え、各LLMが生成した推奨馬番と予想コメントを表示することで、ユーザーの馬券検討を多角的にサポートする。

### 目的
- LLM予想結果を格納するSupabaseテーブルを設計し、Prismaスキーマに反映する
- レース詳細画面にLLM予想専用コンポーネントを新設し、各LLMの予想結果を視覚的に表示する
- 将来的なLLMプロバイダー追加を容易にする拡張可能なテーブル設計を実現する
- 既存の予想スコア（`Predict`モデル）と共存し、予想の多様性を提供する

### 責務分担

| 担当 | 内容 |
|------|------|
| ユーザー（オーナー） | LLMを呼び出して予想を生成し、Supabaseに格納するパイプライン |
| Horecast（本PRDのスコープ） | Supabaseテーブル設計・Prismaスキーマ・API・UIコンポーネント |

## 成功指標（KPI）

### プライマリーKPI
- **LLM予想表示成功率**: 95%以上（レース詳細ページを開いた際にLLM予想が正常表示される割合）
- **LLM予想コンポーネントの閲覧率**: レース詳細ページ訪問者の60%以上がLLM予想セクションをスクロールして閲覧（3ヶ月後）
- **ページロード影響**: LLM予想コンポーネント追加後もレース詳細ページの初期表示が3秒以内

### セカンダリーKPI
- **LLMプロバイダー追加コスト**: 新しいLLMプロバイダーの追加がテーブル変更なし・1日以内（開発工数）で完了できること
- **APIレスポンス時間**: `/api/races/[id]/llm-predict` が500ms以内に応答する割合95%以上（DBからの取得のみのため）

## 機能要件

### コア機能（MVP）

#### 1. LLM予想テーブル設計（Prismaスキーマ）

**ユーザーストーリー**:
Horecastオーナーとして、LLMの予想結果をSupabaseに格納するために、拡張可能なテーブル設計が欲しい

**受け入れ条件**:
- [ ] `LlmPredict` モデルがPrismaスキーマに追加されている
- [ ] `provider` フィールドでLLMプロバイダー名（"openai", "claude"等）を識別できる
- [ ] `first_pick` フィールドで◎推奨馬番（1-18）を格納できる
- [ ] `second_pick` フィールドで○推奨馬番（1-18）を格納できる
- [ ] `third_pick` フィールドで▲推奨馬番（1-18）を格納できる
- [ ] `fourth_pick` フィールドで△推奨馬番（1-18）を格納できる
- [ ] `comment` フィールドで予想コメント（テキスト）を格納できる
- [ ] 新しいLLMプロバイダー追加時にテーブル変更が不要な設計である
- [ ] Prismaマイグレーションファイルが生成されている

**優先度**: P0（必須）

---

#### 2. LLM予想取得APIエンドポイント

**ユーザーストーリー**:
Horecastユーザーとして、レース詳細ページでLLMの予想を確認するために、DBからLLM予想を取得するAPIが欲しい

**受け入れ条件**:
- [ ] `GET /api/races/[id]/llm-predict` エンドポイントが実装されている
- [ ] レースIDに紐づく全LLMプロバイダーの予想結果をまとめて返す
- [ ] `LlmPredictResponse[]` のフラット配列形式でレスポンスを返す
- [ ] データが存在しない場合は空配列を返す（エラーにならない）
- [ ] キャッシュなし（`cache: 'no-store'`）でリアルタイムデータを返す

**優先度**: P0（必須）

---

#### 3. LLM予想表示コンポーネント（LlmPredictSection）

**ユーザーストーリー**:
競馬ファンとして、レース詳細ページで各LLMの予想を見るために、LLM予想専用のUIコンポーネントが欲しい

**受け入れ条件**:
- [ ] レース詳細ページ（`/races/[id]`）の出馬表直下にLLM予想セクションが表示される
- [ ] 各LLMの名前（「OpenAI」「Claude」等）がラベルとして表示される
- [ ] 各LLMの推奨馬番と推奨順位（◎○▲△）が表示される
- [ ] 各LLMの予想コメントが表示される
- [ ] LLM予想ロード中はスケルトンローダーが表示される
- [ ] LLM予想が存在しない場合は「予想データなし」と表示され、ページ全体はクラッシュしない
- [ ] モバイル・PC両方で適切に表示される（レスポンシブ対応）

**優先度**: P0（必須）

## 非機能要件

### パフォーマンス
- LLM予想APIのレスポンス時間: 500ms以内（DBからの取得のみ）
- LLM予想コンポーネントはクライアントサイドで非同期取得し、ページ初期表示をブロックしない
- レース詳細ページの初期表示時間: LLM予想コンポーネント追加後も3秒以内

### ユーザビリティ
- LLM予想の読み込み中はスケルトンUIを表示し、コンテンツシフトを防ぐ
- 予想コメントはモバイル画面でも読みやすいレイアウトとする
- 推奨馬番は既存の◎○▲マーク体系と統一した視覚表現を使用する

### 信頼性
- LLM予想データが存在しない場合もページが正常に表示される
- DB接続エラー時はユーザーフレンドリーなエラーメッセージを表示する
- LLM予想機能の障害がレース詳細ページ全体の表示に影響しない

### セキュリティ
- Supabaseへのアクセスは既存の`DATABASE_URL`・`DIRECT_URL`環境変数を使用する
- LLM予想データはレース公開情報のみを含み、個人情報を含まない

### スケーラビリティ
- LLMプロバイダーを追加する際、テーブル変更・APIルート変更・UIコンポーネントの大幅変更が不要な設計とする

## スコープ外

明示的にスコープ外とする項目:
- LLMを呼び出して予想を生成するパイプライン（ユーザーが担当）
- Supabaseへの予想結果の書き込み処理（ユーザーが担当）
- LLM予想に基づく自動馬券購入機能
- ユーザーごとのLLM予想カスタマイズ（プロンプト編集など）
- LLM間の予想結果の統合・アンサンブル処理
